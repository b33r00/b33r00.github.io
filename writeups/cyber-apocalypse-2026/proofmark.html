Proofmark

Cyber Apocalypse 2026 mobile / reverse engineering hard
HTB{p3rf3ct_f4c3_tru3_sp1n3}

overview

Android APK built on the Godot engine. A 3D scene: you walk into a forge, reach an anvil that runs an "assay" on a ring. The mechanic is to trick that assay into certifying a forged piece — when it accepts, it returns the flag as a certificate string.

Almost none of the verification logic lives in GDScript. It is in a small stripped native library shipped as a GDExtension. This challenge is ARM64 reversing wearing a game as a costume.

initial recon

file proofmark.apk
unzip -l proofmark.apk

Contents: classes*.dex, two libgodot_android.so builds (arm64 + x86_64), and assets/ with .gdc scripts, .tscn.remap scene files, project.binary, assets.sparsepck. A Godot export — logic is not in the dex at all.

The key file was assets/proofmark.gdextension:

[configuration]
entry_symbol = "proofmark_library_init"
compatibility_minimum = "4.7"

[libraries]
android.release.arm64 = "res://bin/android/libproofmark.arm64.so"

A 9.8 KB custom native library next to the huge engine binary. That is the actual target.

analysis

recovering gdscript source

Compiled .gdc bytecode — pulled GDRE Tools and ran a full project recovery:

./gdre_tools.x86_64 --headless --recover=proofmark.apk --output=recovered

Got back readable .gd source for all scripts. The mechanic: GameState keeps three wards values (clamped 0–24) and a bite computed as bite = wards[0] + wards[1]*2 + wards[2]*3. Walking through trigger zones nudges wards by fixed steps. Every change calls ForgeClient.reseal(snapshot). Stepping onto the anvil calls:

func strike(state: PackedByteArray, hallmark: int) -> Array:
    var v: int = _native.submit(state.decode_s32(0), state.decode_s32(4),
        state.decode_s32(8), state.decode_s32(12), hallmark)
    var mark: String = _native.certificate() if v == Verdict.ACCEPTED else ""
    return [v, mark]

The real check lives inside the native Proofmark class. Three exposed methods: reseal(), submit(), certificate().

reversing the native library

apt-get install -y binutils-aarch64-linux-gnu radare2
aarch64-linux-gnu-nm -D --defined-only libproofmark.arm64.so
r2 -A -q -c "afl; iz" libproofmark.arm64.so

Only three real functions: proofmark_library_init (GDExtension boilerplate) and two at 0x1af4 and 0x1ff4.

fcn.00001af4 is reseal() — a small hand-rolled bytecode interpreter running a program from .rodata over the state buffer.

fcn.00001ff4 is the core of submit(). Key gate in the disassembly:

cmp x8, 0x0000004300000053   ; wards0=0x53, wards1=0x43
ccmp x9, 0x000001ce00000037  ; wards2=0x37, bite=0x1ce
b.ne -> return 0  (REJECT_STATE)

In decimal: wards0=83, wards1=67, wards2=55, bite=462. Wards are clamped 0–24 in gameplay. These values are unreachable by playing normally — the whole point of the story.

Past that gate: 1,198,464 iterations of a MurmurHash3-style fmix32 round:

t = h + 0xc2b2ae35
t ^= t >> 16
t *= 0x85ebca6b
t ^= t >> 13
t *= 0xc2b2ae35
h = t ^ (t >> 16)

Then XOR-decrypts a 28-byte blob embedded at offset 0x580 using the top byte of each round's intermediate value as the keystream byte. Checks first four decrypted bytes against "HTB{", returns ACCEPTED (2) and copies out the certificate only on match.

vulnerability

The state check and the hallmark check are independent. There is no cryptographic binding between "this specific ring" and "this specific hallmark". The state is a fixed constant, and the cipher is a 32-bit keyspace built entirely of invertible operations.

Every operation in the round function — add, xor-shift, multiply by odd constant — is invertible mod 2^32. The entire 1,198,464-round chain is a bijection. A 32-bit keyspace with a fully invertible, non-authenticated stream cipher is brute-forceable, and because it is invertible you only need to brute-force the cheap first few keystream bytes.

exploitation

step 1 — emulate first to verify the model

Rather than hand-simulating over a million rounds, I set up a Unicorn ARM64 harness to run the real function. First attempt failed — turned out I had mapped segments by file offset instead of p_vaddr. Fixed by parsing program headers properly. After that the emulator ran cleanly and matched a Python re-implementation byte for byte.

step 3 — brute force the seed with numpy

def F_vec(x):
    t = x + np.uint32(0xc2b2ae35)
    t ^= t >> np.uint32(16)
    t = t * np.uint32(0x85ebca6b)
    t ^= t >> np.uint32(13)
    t = t * np.uint32(0xc2b2ae35)
    y = t ^ (t >> np.uint32(16))
    return y, t

# round 0: scan all 2^32 seeds, keep where top byte == 0x62
# round 1..3: advance survivors one more round each, filter on next byte

Inverted the seed derivation and the 1,198,464-round chain analytically using modular inverses of the two odd multiplication constants:

Patching the .so to force the "HTB{" branch to always pass gets you an accepted verdict but certificate() returns garbage — the ciphertext was never actually decrypted correctly.



takeaway


When a native check gates on two independent conditions checked in sequence, look at whether they are cryptographically bound to each other or just sequential. Independent checks can be satisfied independently.


Whenever every step of a "hash" is reversible and the keyspace is small, the problem is an inversion problem, not a brute-force problem. That changes "computationally infeasible" to "a few seconds of numpy."


Set up the Unicorn emulation harness early. It catches transcription mistakes in hand-read disassembly immediately and turns "re-derive the hash by hand" into "run the real code with the input you want."
